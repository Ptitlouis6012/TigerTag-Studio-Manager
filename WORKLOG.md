## Changed
- **Duplicating spools: a quantity you pick, not one you click up to.** The `−  N  +` stepper meant thirty clicks for a box of thirty identical spools. It is a dropdown now — 1 to 9 for the everyday case, then a **10+** entry that swaps the control for a free field, so the long tail costs one keystroke. Both stop at **50**: every copy is a Firestore document, so a slipped keystroke is a slipped inventory. That ceiling was already enforced inside `duplicateSpoolAsCloud` but the UI could not state it — it is a named `DUP_MAX` shared by both now, so the control never offers what the write would silently clamp. The free field corrects AS YOU TYPE rather than refusing at commit (the reflex the add-product floors already use), and an empty field is left alone mid-edit instead of being fought. Requested by @ImNanou (#26) — `renderer/inventory.js`, `renderer/css/70-detail-misc.css`

## Fixed
- **Creality: the nozzle temperatures set on a filament slot never reached the printer.** The firmware keeps `minTemp` / `maxTemp` from `modifyMaterial` ONLY when the JSON number is written with a decimal point, and drops an integer in silence — the printer still answers without an error. Tiger Studio built the frame with `JSON.stringify`, which writes `190` and can never write `190.0`: in JavaScript the two are the same Number. So every temperature it sent was stored as 0. The mobile app never hit it because Dart serialises a double as `190.0`. The frame is now built by `buildModifyMaterialFrame`, a pure module that swaps the three float fields for placeholders, stringifies, then writes them back as decimal literals — escaping of every other field is still JSON.stringify's, and the integer fields stay integers. Measured on an Ender-3 V4 + CFS, slot 1D, read back with `get boxsInfo`: Tiger Studio's new frame `211.0 / 236.0` → **211 / 236**; the same frame serialised the old way `212 / 237` → **0 / 0**; the slot was then restored and read back identical to its initial state. `PROTOCOL.md` showed `"minTemp": 190` in its own example with nothing to warn that an integer is ignored; both protocol docs now carry the measurement, plus three more measured rules — `rfid` is kept only when vendor + type + name match the printer's own material library, `pressure` is kept either way, and `type` is the material family, not the label.
  - **The material a slot declares now matches what the firmware expects.** The edit sheet sent the picked LABEL as `type` ("PLA High Speed", "PLA+", "Hyper PLA") and built `name` as vendor + label, so `type` was often invalid and `name` matched no profile — `rfid` was reset to "0". `type` is now the family from the material database (`material_type` + `-filled_type`), and vendor / type / name / rfid are taken VERBATIM from the printer's own library when a profile fits: by Creality id under the chosen brand, then the brand's plain "<vendor> <family>" profile, then the exact name under another brand — the picker offers "Hyper" as a vendor, but the printer files that line under Creality. No fit sends `rfid "0"` on purpose. The library was already requested at connection (`reqMaterials`) and its reply never read; it is kept on the connection now. Against the real 18-profile library of the Ender-3, `rfid` becomes keepable for 11 of the picker's 23 combinations (4 before) and `type` is a valid family for all 23 (18 before). Read back on slot 1D: *Creality + PLA High Speed* → `01001 · Hyper PLA` kept; *Hyper + PETG* → `06002 · Hyper PETG` kept; the old composition → `rfid "0"`; slot restored and read back identical.
  - Verified with the frame-building module the app itself uses, over a direct WebSocket — not from the running app, which could not start alongside the installed release holding the single-instance lock — `renderer/printers/creality/{material-frame.js,index.js,PROTOCOL.md}`, `docs/creality-websocket-protocol.md`
