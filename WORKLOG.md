# Worklog — v2.26.2 (in progress)

## Added
- **A custom tax rate, for every case a list cannot hold.** A *Custom* entry at the foot of the country picker opens a panel of its own: the rate, the currency code and the symbol, each with a label and an example — "10" says nothing until you are told it means ten percent. The rate alone would not have been enough either: whoever's country is missing from the list would have kept a euro sign on every price, so the currency travels with it. The entry resolves through a sentinel code checked BEFORE the table lookup, because `_vatEntryFor()` does not find `CUSTOM` and falls back to France — an unrecognised code does not fail, it silently bills you 20%. Values are clamped and shaped where they are READ rather than trusted from the document — the rate to 0-100, the currency to at most three letters — since `currency` also travels to the telemetry roll-up, which expects ISO 4217. Seeding the fields skips whichever one has focus, so a save never rewrites what is being typed, and the fields commit on blur rather than on every keystroke. Stored as three flat fields on `users/{uid}` beside `vatCountry`: no rules change, that document is not field-whitelisted. Verified against the live account and restored afterwards — `brl` normalised to `BRL`, a rate of 250 clamped to 100 — `renderer/inventory.{html,js}`, `renderer/css/60-modals.css`, `renderer/locales/*.json`
- **Canada, with CAD and a rate per province.** All 13 provinces and territories, not the four the request named — half the country's users would otherwise have had no entry. No province SELECTOR was needed and none was built: `_vatEntryFor()` matches `code` as an opaque string, never parsing it or assuming two letters, so `CA-QC` is as valid a key as `FR`, and the picker already renders `label · rate% · symbol` — which is exactly the `Canada (Quebec) · 14.975% · CA$` the request asked for. Zero code, zero migration: `vatCountry` is a free field on `users/{uid}`, and the telemetry's `country` is derived from the locale, not from this, so a sub-national code cannot reach the roll-up that expects ISO-2. `rate` is the COMBINED rate a buyer pays — Canada has no national one, GST being federal with HST, PST, RST or QST layered on per province — and a new `note` field records what each is made of, so whoever updates them next can see it (Nova Scotia moved 15 → 14 in April 2025). Verified against the CRA's own rate table rather than copied from the request. The symbol is `CA$`, not `$`: a Canadian and an American dollar have to be told apart. Requested by @ImNanou (#23) — `data/vat-rates.json`

It reuses the existing community nudge machinery rather than adding a parallel one — the badge, the one-shot notification and the per-account "seen" flag synced to Firestore all come from the shared `COMMUNITY` table, so the entry IS the wiring. ## Changed
- **The "Search" view is called "Catalogue".** It never was a search — it is the official TigerTag+ catalogue, 13 408 products, sitting beside the user's own stock; naming it after the box you type in described the tool instead of the thing. Everything around it already said so: the markup ids (`vtgCatalog`), the view modes (`catalogGrid` / `catalogTable`), the mode test (`_isCatalogMode`) and the material-source entry ("From Catalogue") — only the label the user reads disagreed. The i18n key was renamed with it (`viewGroupSearch` → `viewGroupCatalog`), so it matches its four siblings and the next reader is not sent looking for a search feature — `renderer/inventory.html`, `renderer/locales/*.json`
- **Scanning a code in the inventory now lands on ONE spool.** The inventory already searched `sku` and `barcode` — it just did it by plain substring, so a barcode gun firing `5907753138491` was answered correctly while a shorter prefix was not: Rosa3D's whole range shares `590775313`, and that scan returned 27 spools. A query that LOOKS like a code (six characters or more, carrying a digit, no spaces) is now matched exactly first against SKU, barcode and UID, and only the exact hits are shown — the rule the catalogue already applied, now shared rather than reimplemented: the predicate that decides what looks like a code moved above both searches so the two cannot drift. When nothing matches exactly the ordinary search still runs, so a mistyped code is answered normally instead of locked to an empty view, and anything under six characters (`1000`, `220`, `1.75`) is never treated as a code at all — `renderer/inventory.js`
- **The inventory search says what it can find.** Its placeholder listed material, brand, colour and UID while SKU and barcode had been searchable all along — a capability nobody could guess, on the one field where guessing is the whole interaction. The catalogue's placeholder already named both — `renderer/locales/*.json`
- **A rack shelf can be four spools deep**, up from three. The ceiling lived in three places, and only one of them was a number: the stylesheet ENUMERATED the rows one by one, so a fourth would have been drawn flat on top of the others — no offset, no shadow — and silently, since nothing fails when a selector simply does not match. The renderer now writes each row's index as `--plane` and one rule places any depth from it, reproducing the ladder the enumerated rules used (front row on top, then behind it) because the shelf ABOVE depends on that exact scale to paint over the row below — `renderer/inventory.js`, `renderer/inventory.html`, `renderer/css/30-racks.css`
- The **X1E shows an X1E** in the add form, instead of an X1C. Its own artwork had been sitting unused in the folder since the model was added — `data/printers/bbl_printer_models.json`
- **The bundled TigerTag database is refreshed** — 13 239 products across 65 brands, so a fresh install starts from a current catalogue instead of downloading the delta on first launch. Two version rows were renamed upstream (`TIGER_TAG_MAKER_V1.0` → `TIGER_TAG_V1.0`, `TIGER_TAG_PRO_V1.0` → `TIGER_TAG_PLUS_V1.0`); nothing in the app matches on those strings — the ids and the signing keys are unchanged — but `docs/rfid-vendors/tigertag.md` quoted the old ones and is corrected — `assets/db/tigertag/*`, `docs/rfid-vendors/tigertag.md`

## Fixed
- **Product images: a queue, a size that fits, and two retries.** Three faults in one path. (a) THE BURST — opening the catalogue mounts ~166 cards at once, and `loading="lazy"` did not save us: measured, 163 of those 166 were fetched while 24 were on screen. Over HTTP/1.1 the browser's six-connections-per-origin cap throttled this for free; the CDN speaks HTTP/2, where each request is a concurrent stream on one connection and that ceiling is gone. It is put back in code: an IntersectionObserver (600 px margin) decides WHEN an image is wanted and a queue caps how many are in flight at six. A cap beats a delay between requests — it speeds up on a fast link and holds back on a slow one, with no number to guess. Now 24 load and 14 wait. (b) THE SIZE — the CDN serves SEVEN square renditions (icon 16 px / 429 B … master 1024 px / 101 kB) and the endpoint defaults to `large`; the app took the default everywhere, spending 33 kB to paint a 28 px table chip. Each site now asks for the first rendition that covers its slot at the screen's pixel density, rounding UP — oversized is invisible, undersized is visibly soft. The catalogue table went from 33 kB to 3.4 kB per row. A grid card measures 326 device pixels, so it still legitimately asks for `large`: the waste was never there. Only `cdn.tigertag.io/img` links are rewritten — a user's own photo is any URL at all, and the two detail-panel images keep `large` deliberately. Nine call sites in all: table and list chips, both catalogue views, grid cards, product chips, the reorder card, rack slot photos, the TigerTag import preview and the low-stock notification. (c) THE GIVE-UP — each of the three sites drawing a photo hid or removed it on the FIRST error, turning a momentary failure into a permanent one for the session; and momentary is what they were, every failed URL loading fine on a second request in 223-636 ms. Two retries backing off 400 ms then 1400 ms, then the placeholder, on a URL re-set byte-identical so the CDN cache still answers. `load` and `error` do not bubble, hence capture listeners — which is also how one rule covers the inventory grid, both catalogue views and the product lists instead of three inline handlers free to drift apart, and a MutationObserver picks the images up wherever they appear rather than trusting five render sites to call a scan — `renderer/inventory.js`
- **Adding a printer while a printer's side-card was open opened the brand picker BEHIND it.** Invisible, with nothing to say anything had happened — the click simply looked ignored. The two cards are laid out by different functions that know nothing of each other: `_syncPrinterAddPanels()` places the picker and its choice cards, `_syncPanels()` owns the printer/spool/container stack, and both dock to the same right edge. The picker now closes that stack on the way up rather than trying to cascade past it: you are adding a NEW printer, so the machine on screen has stopped being the subject. The edit form is closed too, or the same overlap just moves one layer down — and closing the panel properly tears its camera down, which a card hidden behind another would otherwise have kept streaming for nothing. Verified in the running app: the panel leaves, the picker lands fully on screen, and nothing is painted over it — `renderer/inventory.js`
- **In dark mode, every community notification wore a BLACK logo on its brand colour.** The glyph was painted with `--surface` — the card background — which is `#ffffff` in light and `#171a22` in dark, so it was white by coincidence rather than by intent, and the comment two lines above it had been claiming "white logo" all along. It is `--on-accent` now: the fixed-polarity token for something sitting ON a filled colour, already used by the low-stock chip right below and by the sidebar buttons — which is exactly why those looked right in both themes while the notifications did not. Discord, GitHub, MakerWorld and the Shop were all affected; the new Wiki chip is simply where it was noticed — `renderer/css/20-friends.css`
- **An H2C reporting `O1C2` was not recognised.** The machine answers with either of two model codes and only one of them was mapped, so the same printer resolved to its catalogue entry or to "Select Printer" depending on which it sent — and unresolved means a "?" thumbnail and no camera transport picked — `renderer/printers/bambulab/probe.js`
