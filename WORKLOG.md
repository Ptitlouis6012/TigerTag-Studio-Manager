## Changed
- **Delete says it must be held — and the two Delete buttons are now one button.** People clicked Delete, saw nothing happen and gave up long before the 1.5 s hold completed. Hovering a Delete now says so, and nothing else: "Hold 1.5 s to confirm". The hint is an opt-in on `setupHoldToConfirm` (`{ hint: true }`) that stores only the DURATION it was given, and writes the sentence when the bubble shows: it can never announce a different hold than the one enforced, and it follows a language change on the selection bar's button, which is wired once at startup. It reuses the shared `#toolInfoPop` bubble, and hovering the ⓘ that the toolbox row also carries still shows the ⓘ's own explanation rather than this one. The spool toolbox's "Remove from inventory" is renamed **Delete** — the same wording as the selection bar in all 9 locales — and takes that button's solid red. The two share the same CSS rules instead of each carrying a copy, so they cannot drift; the dark hold sweep comes with them, since the default red fill would be invisible on a red button. Only Delete changes: erase and recycle act on the chip rather than the record and keep the soft tint. The hint then went to EVERY red hold-to-confirm button, not only the two Deletes: deleting a list, stopping the tracking of a product to reorder, removing a product from a list, stopping a print, deleting a printer (menu and form) and deleting a rack (menu and form). In the two context menus it is keyed on the danger class, so "Empty the rack", held but not red, is left as it was. The amber `danger-soft` holds (unlink a twin, remove from rack, clear TD) and the non-destructive ones (duplicate, repair, empty) do not show it. The rack and printer Delete buttons also explained the hold through a native `title`, hard-coded in English on the rack; those are gone, since two bubbles would stack — `renderer/inventory.js`, `renderer/css/70-detail-misc.css`, `renderer/locales/*.json`
- **Duplicating spools: a quantity you pick, not one you click up to.** The `−  N  +` stepper meant thirty clicks for a box of thirty identical spools. It is a dropdown now — 1 to 9 for the everyday case, then a **10+** entry that swaps the control for a free field, so the long tail costs one keystroke. Both stop at **50**: every copy is a Firestore document, so a slipped keystroke is a slipped inventory. That ceiling was already enforced inside `duplicateSpoolAsCloud` but the UI could not state it — it is a named `DUP_MAX` shared by both now, so the control never offers what the write would silently clamp. The free field corrects AS YOU TYPE rather than refusing at commit (the reflex the add-product floors already use), and an empty field is left alone mid-edit instead of being fought. Requested by @ImNanou (#26) — `renderer/inventory.js`, `renderer/css/70-detail-misc.css`

- **Erasing or recycling a chip goes through the guided chip window instead of a blind hold.** "Erase the TigerTag / TigerTag+" and "Recycle to NFC" used to be hold-to-confirm rows that only unlocked once the chip(s) were already on the readers, and then reported progress in the row label. They are plain buttons now, usable as soon as a reader is connected, and open the same window as a TigerData burn or a chip update: one card per reader turning blue when THIS spool's chip sits on it and red when a foreign chip does, the action button disabled until every chip of the spool (both, for a twin pair) is in place, then the sequence-wide progress bar while writing. The window's title is the action itself ("Erase the TigerTag+" / "Recycle to NFC"), and its red Erase / Recycle button is held 1.5 s, with the hold hint on hover — a dedicated `#cemReset` button, since Burn and Update stay plain clicks. A wrong chip now reads "That's not this material's chip" (no mention of a spool), and the chip cards no longer print the UID, which debug mode used to show. The window no longer changes height as the write goes on: a message (wrong chip, failure, same chip twice, no reader) now replaces the "Hold the NFC tags in front of the readers" line in red instead of appearing on a line of its own below, the progress bar is always on screen (empty until a chip is written), and the button row is hidden during the write without giving up its space — every chip window (burn, update, erase, recycle) used to grow and shift under the user's hands. On a verified write the window closes, the Xano events fire per verified chip (`reset` / `nfc_init`, unchanged), and the spool is removed from the inventory as before; a failure keeps the window open on Retry. Implemented as two more modes of the update flow (`openUpdateModal(r, "format" | "recycle")`, `_cemStartUpdate` routing to `formatRfidTag` / `eraseRfidTag`) rather than a third copy of the gating — `renderer/inventory.js`, `renderer/css/60-modals.css`

## Fixed
- **Creality: the nozzle temperatures set on a filament slot never reached the printer.** The firmware keeps `minTemp` / `maxTemp` from `modifyMaterial` ONLY when the JSON number is written with a decimal point, and drops an integer in silence — the printer still answers without an error. Tiger Studio built the frame with `JSON.stringify`, which writes `190` and can never write `190.0`: in JavaScript the two are the same Number. So every temperature it sent was stored as 0. The mobile app never hit it because Dart serialises a double as `190.0`. The frame is now built by `buildModifyMaterialFrame`, a pure module that swaps the three float fields for placeholders, stringifies, then writes them back as decimal literals — escaping of every other field is still JSON.stringify's, and the integer fields stay integers. Measured on an Ender-3 V4 + CFS, slot 1D, read back with `get boxsInfo`: Tiger Studio's new frame `211.0 / 236.0` → **211 / 236**; the same frame serialised the old way `212 / 237` → **0 / 0**; the slot was then restored and read back identical to its initial state. `PROTOCOL.md` showed `"minTemp": 190` in its own example with nothing to warn that an integer is ignored; both protocol docs now carry the measurement, plus three more measured rules — `rfid` is kept only when vendor + type + name match the printer's own material library, `pressure` is kept either way, and `type` is the material family, not the label.
  - **The material a slot declares now matches what the firmware expects.** The edit sheet sent the picked LABEL as `type` ("PLA High Speed", "PLA+", "Hyper PLA") and built `name` as vendor + label, so `type` was often invalid and `name` matched no profile — `rfid` was reset to "0". `type` is now the family from the material database (`material_type` + `-filled_type`), and vendor / type / name / rfid are taken VERBATIM from the printer's own library when a profile fits: by Creality id under the chosen brand, then the brand's plain "<vendor> <family>" profile, then the exact name under another brand — the picker offers "Hyper" as a vendor, but the printer files that line under Creality. No fit sends `rfid "0"` on purpose. The library was already requested at connection (`reqMaterials`) and its reply never read; it is kept on the connection now. Against the real 18-profile library of the Ender-3, `rfid` becomes keepable for 11 of the picker's 23 combinations (4 before) and `type` is a valid family for all 23 (18 before). Read back on slot 1D: *Creality + PLA High Speed* → `01001 · Hyper PLA` kept; *Hyper + PETG* → `06002 · Hyper PETG` kept; the old composition → `rfid "0"`; slot restored and read back identical.
  - **Verified through the app's own Save button**, with the WebSocket `send` intercepted so the frame recorded is the one the app actually emitted. *Generic + PETG* → emitted `00003 · Generic · PETG · "Generic PETG" · 220.0 / 270.0` → read back 220 / 270, rfid `00003` (the slot held 190 / 240 before, so the write is proven, not coincidental). *Creality + PLA High Speed* → emitted `01001 · Creality · PLA · "Hyper PLA" · 190.0 / 240.0` → read back `01001 · Hyper PLA`, temperatures back from 220 / 270 — and "Hyper PLA" can only have come from the printer's library, so the running app does read `retMaterials`. Slot restored and read back identical — `renderer/printers/creality/{material-frame.js,index.js,PROTOCOL.md}`, `docs/creality-websocket-protocol.md`
