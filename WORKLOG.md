# Worklog — v2.26.2 (in progress)

## Added
- **Two more Bambu Lab machines: the A2L and the X2D.** Both were already in the printer catalogue but neither reached the connection tutorial, so picking one offered no walkthrough at all — and the X2D was wearing an X1C's photograph. The A2L joins the **A-series** walkthrough (the one the A1 and A1 mini use) and the X2D the **X / H / P** one; that second walkthrough is a single shared series already — the X1C, the H2 range and the P2S have been reading the same seven steps for months, so there is no separate X-series tutorial left to retire. Each model's own picture now appears both in the add form and in the tutorial's model picker. Both are also RECOGNISED on sight: a scanned or cloud-added printer is matched by the `DevModel` code it reports, and neither code was known — `N9` for the A2L, `N6` for the X2D — so either machine would have arrived as "Select Printer", with a "?" thumbnail and no camera transport chosen. The codes are read off Bambu Studio's own `resources/printers/<CODE>.json`, each carrying the machine's `display_name`, rather than inferred from a serial glimpsed in the wild. The same files settle both open questions: Bambu files the A2L under `series_n` with the A1 and A1 mini, and the X2D under `series_x1` with the X1C and the P2S — the two walkthroughs they were given — and their camera blocks match those families exactly, the A2L advertising a LOCAL liveview like an A1 (JPEG over TCP) and the X2D none, like a P2S (RTSP). No serial prefix is recorded for either: a prefix can only be read off a real machine, and the code is the path discovery and the cloud both take — `data/printers/bbl_printer_models.json`, `renderer/printers/bambulab/{tutorial.json,probe.js}`, `assets/img/bbl_printers/{a2l,x2d}.png`, `assets/img/tutorials/bambulab/models/{a2l,x2d}.png`

## Changed
- **A rack shelf can be four spools deep**, up from three. The ceiling lived in three places, and only one of them was a number: the stylesheet ENUMERATED the rows one by one, so a fourth would have been drawn flat on top of the others — no offset, no shadow — and silently, since nothing fails when a selector simply does not match. The renderer now writes each row's index as `--plane` and one rule places any depth from it, reproducing the ladder the enumerated rules used (front row on top, then behind it) because the shelf ABOVE depends on that exact scale to paint over the row below — `renderer/inventory.js`, `renderer/inventory.html`, `renderer/css/30-racks.css`
- The **X1E shows an X1E** in the add form, instead of an X1C. Its own artwork had been sitting unused in the folder since the model was added — `data/printers/bbl_printer_models.json`
- **The bundled TigerTag database is refreshed** — 13 239 products across 65 brands, so a fresh install starts from a current catalogue instead of downloading the delta on first launch. Two version rows were renamed upstream (`TIGER_TAG_MAKER_V1.0` → `TIGER_TAG_V1.0`, `TIGER_TAG_PRO_V1.0` → `TIGER_TAG_PLUS_V1.0`); nothing in the app matches on those strings — the ids and the signing keys are unchanged — but `docs/rfid-vendors/tigertag.md` quoted the old ones and is corrected — `assets/db/tigertag/*`, `docs/rfid-vendors/tigertag.md`
