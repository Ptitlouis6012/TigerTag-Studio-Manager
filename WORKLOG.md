# Worklog — v2.20.1 (in progress)

## Added
- **A filter field inside the long filter dropdowns** (Brand, Material, Aspect, Type, Tag, and the Search views' own selectors). Replacing a native `<select>` with a styled popup quietly cost the one thing the browser gave for free — reaching a name by typing it — and with 124 brands in the list that meant scrolling past a hundred names. Typing narrows the list instead of jumping to a letter: the keyboard goes somewhere visible rather than into a hidden buffer whose state you have to guess. It matches **anywhere** in the name, not just the start ("sun" finds both Sunlu and eSun), ignores case and accents, and lands the cursor on the first survivor so Enter always means "the obvious one"; the arrow keys walk what is left. Only on lists of 8 or more — on a five-line list a search box is furniture. — `renderer/inventory.js`, `renderer/css/70-detail-misc.css`

- **Shelf depth** — a rack can now hold spools one behind the other (1 to 3 rows deep). Storage draws the depth in perspective: each row back is the same grid, pushed up and sideways so the spool behind stays readable, front row on top. — `renderer/inventory.js`, `renderer/css/30-racks.css`, `renderer/inventory.html`
  - Rack doc gains `depth`, written only when > 1; a spool's slot gains `rack.depth`, written only when > 0 (front row). A rack or spool without them is depth 1 / front row, so nothing needs migrating and a depth-1 rack renders byte-for-byte what it rendered before.
  - "Rows deep" stepper in the rack create/edit panel, on its own line under levels and slots per level — three steppers abreast did not fit the panel and the values were being clipped, and the split says something true: levels and slots describe the FACE of the rack, depth describes what sits behind it. Same width as the other two, since a stepper stretched across the row reads as a different kind of control; slot total and preview caption account for it.
  - Shrinking the depth orphans the spools that were behind, same rule `updateRack` already applies when a rack loses rows or columns.
  - Back rows are painted as a solid colour tile instead of a weight bar: the bar is anchored to the bottom of a slot, which is exactly the part a back row hides. Picture view is unchanged — it already draws a full tile, so the illustration shows at every depth.
  - Auto-fill fills the whole front row before anything goes behind it.
  - Slot locks, drag-and-drop, the swap-on-drop, the hover tooltip, the rich stats and the surgical slot patcher all carry the third coordinate. So do "Clear all", auto-unstore of depleted spools, single-spool auto-assign, and the "Storage location" row in a spool's detail — a lock or an occupancy check that ignored the depth was reading the wrong slot.
- **Depth spacing setting** — a "Depth" button in the Storage header opens two sliders (vertical 12–52 px, sideways −30 to +30 px, negative leaning the rows to the left). Stored on the **account** — `users/{uid}.studioRackDepthOffset`, beside `studioTheme` and the other Studio-only settings, so the same spacing greets you on any machine you sign in from: it describes how you want to READ your racks, not the screen you happen to be sitting at. Not in `prefs/app`, which is the cross-app document shared with the mobile app, and which has no rack plan; it rides along with the user-doc read the app already does at boot rather than costing a second fetch, and `users/{uid}` takes it without a rules change (owner-only, blacklist write). Still cached in `tigertag.rack.depthOffset` so a cold start with no network paints the right spacing at once instead of drawing wrong and jumping. Applied as two CSS custom properties so moving a slider repaints without rebuilding a single node. Picture view scales the offsets by tile size, so one setting stays right in both view modes. The button only appears when a rack actually has depth. — `renderer/inventory.js`, `renderer/css/30-racks.css`

- **Colour range filter** — a rainbow bar carrying a hue window, sitting on its own row at the top of Storage, right under the search band: drag its middle to change the shade, pull either edge to widen it. It is always on show — finding a colour is what this view is for, and putting the finder behind a button asked the user to remember it exists. Spools in range stay lit, the rest fade — the rack keeps its shape, so you see *where* on the shelf the colour is. A **second bar** beside it runs white → grey → black for the colours that have no hue at all (below 15 % saturation) — so you can aim at "the light greys" instead of picking from coarse buckets. Neither bar is ever dimmed or tinted: veiling the unselected part would mean the colours you are choosing FROM are not the colours themselves. So the choice is marked by **height** instead — the selection is a **bubble** sitting on the bar, twice its height, corners a touch rounder than the bar's own, lifted by a drop shadow, and it carries a copy of its bar's gradient sized to the whole bar and slid into place, so a bubble taller than the bar still shows the true colours under it. It reads as the colour you picked rather than as a frame drawn around one, and its white ring over a dark hairline survives both a pale yellow and a black. Nothing is ever drawn ON the spectrum: approach an edge and **the bubble's own border thickens on that side**, clipped by its own corner radius, so what invites the grab is the bubble getting a lip rather than a white bar dropped on top of the colours. **Double-clicking inside the bubble puts that bar back to sleep** — dropping a colour constraint is the one filter you undo constantly while hunting, and the reset button would clear the search and the selectors along with it. Both lips grow at once, not just the one under the cursor: the pair reads as the bubble becoming grabbable, where a single lip read as a lopsided bubble. Which edge you will actually take is said by the cursor, which now reads the whole gesture: a crosshair over the open spectrum, an **open hand** over the bubble, a **closed one from the instant you press** — it used to be recomputed only by the hover handler, so pressing changed nothing until you moved a pixel and the grab looked like it had not registered — and the double arrow within reach of an edge, and internally only the nearest edge is armed — on a narrow bubble both are within reach. The button behind it draws nothing at all and is pure hit area, wider than what it grabs; reached by keyboard it outlines itself, since no pointer is there to thicken an edge for it. The **wheel inside the bubble** widens or narrows the range around its own centre, easing between widths rather than stepping: the window is now patched in place instead of being thrown away and rebuilt on every redraw — a replaced element cannot animate from a geometry it never had — and the easing is lifted the moment the notches stop or a drag begins, where a transition would trail the cursor, so the colour you aimed at stays under it and only the tolerance changes — no need to catch a two-pixel edge. Storage zooms on the wheel too, so the bar claims it only with the pointer actually inside the bubble. A handle is centred on its edge by its own box rather than by subtracting half of a hard-coded width, which had them sitting off their own edge as soon as they grew. It opens at the same on-screen width as the hue window rather than spanning the whole scale — a selection covering every neutral at once is a filter that has already given up. Neither bar is captioned — a rainbow and a light-to-dark ramp say what they select on sight, and the names live on as their accessible label. There is only ever **one selector on screen**: it moves to whichever bar you touch, landing where you clicked, and the other bar goes back to being a plain gradient. You are hunting a hue or a shade of grey, never both — a spool cannot be "that orange AND that grey", so running both would have meant the union of two unrelated searches, which reads as a filter that stopped working. Both are driven by the same selector code; the only difference is that hues wrap at red and light-to-dark does not. The filter matches the colours a spool is actually **painted** with, in `colorBg`'s own precedence — the chip carries three colour slots and a mono spool's two spare ones read back as a valid #000000, which had every spool in the inventory answering to "show me the blacks". The window never narrows past 10° so it stays grabbable, and it crosses red (360°/0°) as one range instead of splitting in two. A bicolor matches on either of its colours. Nothing is stored: the hue is derived from the colour already on the spool, and it composes with the search and the quick filters rather than replacing them. No running count beside the bars: the racks themselves already show what survived the filter, and a number repeating it competed with the stats row for the same answer. The two bars are **shared by every view that shows material** — Inventory (table and grid), Favorites, the order list, Search and Storage — not Storage alone. They live in the page shell under the search band rather than inside a view's template, so they are wired once at boot instead of on every render, and the window you set survives switching views: pick a colour and it keeps meaning the same thing wherever you look for it. The match runs on whatever colours the thing in front of you actually has — a spool's up-to-three chip slots, a product identity's colour, and for a catalogue entry the whole `color_info.colors` list, so a bicolor product matches on either of its halves exactly like a bicolor spool does — through one shared rule, over a single hex normaliser: colours arrive as `#RRGGBB` **and** `#RRGGBBAA`, and the second is the common shape (9 548 of the catalogue's 12 211 entries), so anything testing a colour without stripping the alpha silently disqualifies three quarters of the data — 16 brands, CaiLab among them, had no six-digit colour at all and could never match anything, and it composes with the search and the other quick filters exactly like they compose with each other. Hidden where it could not filter anything: the printer views list devices, not material, and Lists show what to buy rather than what you own. The reset is a single refresh glyph at the **head of the search row**, left of the field — it clears every filter, so it belongs where the filtering starts rather than at the end of the colour bars — and it puts back **everything**, not just the colour window — the search box, the brand / material / aspect / type / tag selectors, the ❤ ★ flags and, in the Search views, the catalogue's own selectors: it sits at the end of the filter row and reads as that row's reset, so clearing only the two bars would leave a brand or a half-typed search quietly still on, which is exactly the state that makes a filter look broken. It is dimmed until it has something to undo — still clickable, the click is simply a no-op, but a button that looks ready and then does nothing is what makes people doubt the control. A click that does clear something turns the glyph one full turn, over three notes falling away, and the button stays lit for the whole turn — the filters are gone by the first frame, so dimming it mid-spin would make the acknowledgement look interrupted; it greys out when the glyph comes to rest: with every filter dropping at once the view can look barely different — a search that matched everything, say — and without a visible acknowledgement the click reads as ignored — the label it replaced was the widest thing on the row, and the name lives on as the accessible label. Moving the window only re-runs the dim pass, so the racks are never rebuilt. — `renderer/inventory.js`, `renderer/css/30-racks.css`

- **The storage plan** — racks are placed by hand instead of being packed in creation order.  **Moving a rack needs no mode**: grab it by its header and drag, at any time — it is the frequent, harmless action, and the slots underneath stay what they are, somewhere to drop a spool. The grid shows itself for the length of the drag and gets out of the way after. "Tidy up" sits before the mode toggle in the header — it is an action you take while arranging, and the toggle is the way out, which belongs at the end of the row rather than in the middle of it. "Arrange" is kept for what is neither frequent nor harmless: the resize grips, which edit the rack itself and can send spools back to Not stored, plus a permanent grid and Tidy up. The position lives on the rack as `bento: {x, y}` in 24 px cells, so it follows the account rather than the machine, and it is opt-in: until the first arrangement the packer runs exactly as before. What is *not* stored is a size — a rack's block is exactly as big as the rack inside it, so the grips **edit the rack** (a shelf, a column) and the block can never lie about what it holds. Shrinking asks first, naming how many spools it would send back to Not stored. While a grip is held, a dashed outline shows the footprint the rack is heading for: until now the only thing that moved during a resize was the "3 × 3" badge — the card kept its old box until you let go, so you were sizing a rack blind and found out afterwards. It is drawn above the card, because a shrink lands inside the rack's current box and behind it there would be nothing to see. **Nothing on the plan moves except the rack you are holding.** A rack's place is something the user authors, not a layout the app computes — every version that pushed neighbours aside was writing other racks' positions to the database behind their back, and produced four rounds of "why did that one move?". Free placement instead, kept tidy by magnetism: while dragging, a rack looks for a nearby edge to lock onto — flush against a neighbour, or lined up with its left, right or centre — and falls back to the grid when there is nothing within 8 px to grab. A thin guide line shows which edge it caught, so a rack that snaps never reads as a rack that jumped. Overlapping is allowed — it is the user's plan — but never silent: the card outlines in red while it does, and the rack moved last sits in front of what it covers, like layers in a drawing app. The stacking order is stored with the position, because two racks overlapping with no way to say which is on top makes a plan unreadable. One drag, one document written. Nothing else may re-arrange the board either: the width observer on the racks column is gone — it re-packed on every width change, and the width is now something the plan itself writes, so zooming past the edge of the window fed straight back into a full re-pack — and a window resize re-applies the stored positions instead of packing. Only "Tidy up" re-packs, because the user asked it to.

  Positions are stored in **pixels** (`plan: {x, y}`) rather than grid cells, because racks snap to each other and a neighbour's edge almost never falls on a 24 px line. The first version's cell-based `bento` field is still read as a fallback, so no arrangement is lost and nothing needs migrating.

- **A chime when a new spool joins the inventory** — a bright rising two-note on a square wave, the chiptune "you just gained something" shape, and the only cue in the app meant to feel like a small reward rather than a confirmation. It fires however the spool got there — scanned, typed in, imported, or pushed from another device — because it hangs off the inventory subscription rather than one entry point. Never on the first snapshot, which is the whole inventory turning up at once; once per snapshot, so importing fifty spools rings once and not fifty times; and the ids already announced are remembered, since a local write surfaces twice, once pending and once confirmed by the server. — `renderer/inventory.js`
- **Sounds when a rack is picked up and set down** — a light tick on the grab, a low short thunk on the release, joining the synthesised cues the app already uses (no audio files: they cost nothing to load and can be tuned by ear in the source). Deliberately pitched well below the spool cues, which live around 400-700 Hz: a whole rack landing should not sound like one spool clicking into a slot. The grab tick is the quietest of the set — it fires on every drag — and the drop sounds on every release, including a drop back where it started: the sound answers the gesture, not the outcome. — `renderer/inventory.js`

## Changed
- **"Not stored" lists the most recently added spool first.** A spool lands there the moment it is added, and what you have just scanned is what you are about to put away — it belongs at the top rather than behind everything you racked months ago. Empty spools still sink to the bottom, and are ordered newest-first among themselves too. The date used is the one the card already shows ("Added 5mo ago") — carried by every spool, chip or not: a chipless TigerData entry gets the same `timestamp` when it is created, so the order is never arbitrary. — `renderer/inventory.js`

- **The search row reads as one family of controls.** The field is a pill with an inline **"+"** on its left. In the material views it drops a small menu with the two ways to add — from the official catalogue, or by hand — where a side card used to open just to ask that same question. One glyph and one label per line, nothing else: two choices whose names already say what they do do not need a sentence each. The wording comes from the same source list that card used, so there is one place to change it. In the printer views it opens the brand picker and in Storage the new-rack modal — it **is** the app's add button now, the header's "+ Material" having been folded into it and removed: one add control instead of two, and the one that is where you are already working. Its name follows the view (Material / Device / Rack), and it disappears in a friend's inventory, which is read-only — the same action, within reach of where you are already typing, and it follows that button wherever it goes (Material / Device / Rack) because it delegates to it rather than duplicating its handler; its accessible name is read off that button so the two can never disagree. The icon-only buttons on the row are round and the filter dropdowns are pills, so nothing square sits beside a rounded field. — `renderer/inventory.html`, `renderer/css/70-detail-misc.css`, `renderer/inventory.js`
- The "To order" filter keeps **one glyph whether it is on or off** — a plain cart. It used to be a cart-with-a-plus when off and a plain cart when on, which made the same button look like two different controls depending on its state; colour alone marks it now. — `renderer/inventory.html`, `renderer/css/70-detail-misc.css`

- **Racks are no longer reordered by dragging a grip** — where a rack sits is now where you put it on the plan, not its rank in a list. Two ways to move the same thing is one too many, and the grip's "make room" shuffle fought the plan: grabbing a card silently rewrote `order` behind the arrangement. The `⋮⋮` handle, the reorder writer and their styles are gone; `order` survives as the iteration order used when tidying up. — `renderer/inventory.js`, `renderer/css/30-racks.css`
- Legacy `lockedSlots` keys (`"level:position"`) are now read as "locked at every depth", while new locks are written as `"level:position:depth"`. Unlocking one row of a legacy-locked column keeps the others locked instead of silently freeing them. No document is rewritten. — `renderer/inventory.js`

## Fixed
- **A spool's chip was written with its remaining weight multiplied by a thousand** — a 1 kg spool came back reading `1000000 g`. The chip carries ONE unit byte for BOTH of its quantities (a real 1 kg tag reads `measure: 1, measure_available: 1, id_unit: 35`), while our Firestore document does not follow that convention: `measure` is in the product's unit but `weight_available` is always in grams. The SDK takes one of each and stamps the document's unit on both, so every kg product — 11 242 of the catalogue's 12 211 — went onto the chip a thousand times too heavy, and it compounded: on each rescan the app rewrites a chip whose weight disagrees with the database, which the corruption guaranteed. Converted now at the one boundary where a document becomes a chip, so all three write paths are covered at once. The field is always set and never dropped: the SDK falls back to `measure_gr` when the remaining weight is absent, and that value is in grams too, so leaving it out put the same thousandfold error on the chip by another route — both candidates are converted, nothing reaches the SDK still expressed in grams. A unit coarser than the value rounds (1303 g on a kg tag becomes 1 kg) and says so in the log; the resolution is the format's, not ours, and the next weighing corrects it. A stock entry is also **capped at the spool's own capacity** when it is seeded from a chip: the SDK scales the remaining quantity by the chip's starting unit, so a chip carrying 1000 next to a "kg" unit reports a million grams — and a spool cannot hold more than it holds. That cap is a guard rail rather than a fix for one cause: whatever puts an impossible figure on a chip, whoever wrote it, what enters stock never exceeds its own capacity, and it only ever pulls a value down so a legitimate reading passes through untouched. Verified against the SDK the app ships. — `main.js`, `renderer/inventory.js`
- **A disconnected scale no longer shows a battery level.** The glyph kept displaying the last percentage it had received, which is only what was true when the scale went quiet — minutes or days earlier. A gauge that states a level it cannot know is worse than no gauge: the red glyph already says the device is out of touch, and that is the honest answer. Checked against every state: reporting → shown, on standby → shown, offline → hidden, offline while it was charging → hidden. — `renderer/IoT/tigerscale/index.js`
- **In dark mode you could not tell which view was selected.** The sliding bubble in the view selector conveys its lift with a soft black drop shadow over a raised face — which works on a light ground and does nothing on a dark one: the shadow is invisible against near-black, and the raised face sits five shades above the track (contrast 1.08). It now carries a hairline as well, drawn with `--border-strong`, which is a dark line on light and a light one on dark — the way each ground actually shows a lifted edge. Composited, the line renders at rgb(79,83,96) over a rgb(30,34,44) track: a 2:1 edge instead of nothing. No theme-specific rule, which this stylesheet has none of. — `renderer/css/70-detail-misc.css`
- **Every view started at a different distance from the filter rows.** Each view container declared its own top margin, each with a comment pointing at another one to justify the number — six copies chasing each other, and two had already drifted: Storage and Printers used 4 px of padding where the table, the grid, Favorites, Lists and Search used a 12 px margin. They now all read one `--view-gap` token, so the value exists once and cannot drift again. The grid class was also carrying a top margin of its own, which doubled the gap wherever it is reused **inside** another view — the Favorites grid and the catalogue's grid body both wear it in a container that already spaces itself, so those two sat twice as far from the colour bars as the inventory grid did. The distance belongs to the view container, once. Measured after: 8 px for all seven containers, and nothing added by a nested grid. — `renderer/css/00-base.css`, `30-racks.css`, `40-printers.css`, `70-detail-misc.css`
- **Icons nested in the search field's buttons were being positioned as if they belonged to the field.** `.inv-search .icon` is meant for the magnifier, but as a descendant rule it caught every icon inside every button in the field and pinned it to the field's right edge: the new inline "+" sat 4 px off-centre in its own circle, and the clear button's cross had the same treatment. Scoped to a direct child, which is what it always meant. — `renderer/css/70-detail-misc.css`
- **Three filter dropdowns could sit open at once**, stacked over each other. Each one closes on a click outside itself, but the button that opens a dropdown stops the click from propagating — it has to, or the click would reach that very handler and shut the list a moment after opening it. The side effect is that the OTHER dropdowns never heard about the click either. Opening one now closes the rest explicitly. — `renderer/inventory.js`
- **The Brand filter listed printer brands instead of filament brands** — and with no way back, so a user standing in Storage or Inventory could not filter their own spools by brand at all. The Brand / Material / Tag selects are SHARED between the materials views and the Printers view, which repurposes them (Brand → printer brands, Material → online/offline). The Printers view refreshed them on every one of its renders — and a connected printer pushing a status update re-renders it through a brand callback **whatever the user is currently looking at**. So the filters were rewritten behind the user's back, seconds after leaving the Printers view. The refresh now only runs while the Printers view is the one on screen. — `renderer/inventory.js`
- **A rack's ⋮ menu opened far from its rack** — on the storage plan at 60 % zoom, the menu of the right-hand rack appeared three columns away, and drawn smaller than it should be. The menu is positioned in viewport coordinates so it can escape the rack's own overflow, but it lives inside the plan's scaled container, and a CSS transform makes its element the containing block for everything `position: fixed` underneath it: the coordinates were then read against the plan, not the screen, and scaled on top. Measured on a reproduction: a button at x=1264 opened its menu at x=809, 108 px wide instead of 180. The menu is now parked on `<body>` while open — 0 px off, full size — and put back on its card when it closes, so a re-render disposes of it with the card. It also **dismisses itself as soon as the view moves** — wheel, scroll, a middle-click pan, a click outside or a window resize — because a menu anchored to the viewport cannot follow its rack, and one left hanging over a neighbour still acts on the rack it was opened from. Its own items and its own kebab are exempt, so pressing an item reaches it and pressing the kebab again is still the toggle. Since an open menu no longer sits inside its card, the kebab looks it up by the rack it belongs to as well. — `renderer/inventory.js`
- **A move that only changed the depth did not show** — the spool stayed drawn where it was until some unrelated change forced a redraw, then it jumped to its real place. Storage skips rendering when its signature is unchanged, and that signature listed a spool's rack, level and position but not its depth: moving a spool from the back row to the front of the same column produced an identical signature, so the early-return fired and the view kept the old picture. The write had gone through all along. — `renderer/inventory.js`
- **Back rows were unreachable in picture view** — a spool could not be dropped past the front row. The picture-view scale never applied: `rp-slotview-photo` lands on `#invRackView` itself, so the id rule setting the scale to 1 beat the class rule setting it to 2. The rows stayed 34 px apart while the tiles are 64 px tall, leaving a ~20 px sliver of each back row — too small to see, and too small to aim at. The row's top padding had a second version of the same bug: it read the resolved spacing from a custom property defined on a child, so it fell back to the raw value and ignored the scale too. Measured after the fix: the whole 61 px back tile is hittable, top to bottom. — `renderer/css/30-racks.css`
- The top-most slot now sits at the same height whatever the depth. The column-number line is a row too, so it was getting the depth padding it has no back rows to use — a band of dead space under the rack name that grew with every row of depth added. Measured: 20 px from the grid to the first slot, identical at depth 1 and depth 2. — `renderer/css/30-racks.css`
- Back rows are drawn at the **same size and the same opacity** as the front row. They were scaled down and carried an inset white ring, which made them read as smaller, half-transparent slots — a slot holds the same spool whatever row it sits in, so it is drawn the same. — `renderer/css/30-racks.css`
- Each shelf now isolates its own depth planes, so the front row of one shelf can no longer paint over the back row of the shelf below it. — `renderer/css/30-racks.css`
- Changing the depth spacing re-runs the masonry: the cards get taller and the packer works from measured heights, so without it they kept their old boxes and overlapped their neighbours. — `renderer/inventory.js`
