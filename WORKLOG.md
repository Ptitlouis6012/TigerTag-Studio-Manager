# Worklog — v2.15.0 (in progress)

## Added
- **New app icon, generated from the TigerSystem vector master.** `assets-src/svg/tigersystem_icon.svg` is the single source for every icon the project ships, and it is never rescaled or redrawn: Windows `.ico` (all 7 sizes, 16 → 256), the favicons and the in-app SVG take it exactly as designed, while the macOS `.icns` and the Linux `.png` take the same full-size artwork with only its four corners clipped to a radius — macOS applies no mask of its own, so a raw square would sit in the Dock with hard corners next to every rounded sibling. Regenerate with `node scripts/make-icons.mjs`: it rasterises through headless Chrome (the only renderer here that preserves the alpha the clipped corners need — `qlmanage` flattens onto white) and packs the `.ico` itself, since `app-builder` emits a single 256 px entry from one PNG and crashes on a directory — `assets/img/icon.{icns,ico,png}`, `assets/svg/tigersystem_icon.svg`, `assets/favicon/`, `scripts/make-icons.mjs`.
- **Catalogue search → create a TigerData+.** A new **Search** view segment (grid + table) browses the official TigerTag+ product catalogue; picking a product opens its Product card and one button turns it into a chipless spool already filled with that product's data — nothing to type. Implements `docs/CATALOG-SEARCH-BRIEF.md` (ratified) — `main.js`, `preload.js`, `renderer/inventory.js`, `renderer/inventory.html`, `renderer/css/40-printers.css`, `renderer/css/70-detail-misc.css`.
  - **New tier — TigerData+**: a TigerData carrying a real `id_product`. **Derived, never stored** (`isCloud && id_product ∉ {0, 0xFFFFFFFF}` → `_hasRealProductId`, `normalizeRow.isCloudPlus`); it is explicitly **not** a TigerTag+ — no chip, no UID, so `id_tigertag` keeps the chipless nonce (`_catChiplessNonce` re-rolls off the version table so the row can never read as Plus). Distinct badge via `tierBadgeHTML` (`.tag-cloud-plus`: chipless white capsule, amber accent — never a gold fill, which would read as a TigerTag+).
  - **Import-all-once**: new IPC `catalog:fetch-all` (`main.js`) pages `product/get/all` (`per_page` 1000, follows `nextPage` until null, no hard-coded catalogue size) → cached in `localStorage` (`tigertag.catalog`). The copy refreshes itself once the cache passes **24 h** — the catalogue gains products daily, so a day is the most that can go by unnoticed — and **Settings → Tools** carries a *Re-sync the catalogue* button that forces it immediately, with a line reporting how many products are held and how old the copy is. Search, filters and sort then run **entirely in memory**; after the first sync nothing but a cache rebuild touches the network — plus one `product/get` per product actually opened.
  - **The views reuse the app's own shells rather than restating them**: the grid is `.inv-grid` + `.spool-card` built by `_gridCardInnerHTML` (identical card, identical size, identical wording rules); the table is a real `<table>` in `.table-wrap` with the always-on `.sel-cell` selection pastille, columns illustration · type · material · brand · series · colour · name · capacity; the filter dropdowns are the app's `_enhanceSelect` custom select, showing the field name on the button and a plain "All" in the list.
  - **Filters at parity with the public catalogue page** (`tigersystem.io/…/catalog`): **Type · Brand · Series · Material · Sort**, every option carrying its count, Series scoped to the selected brand and disabled until one is picked, sort by brand / name / material with a stable tiebreak. All of it runs over the local cache.
  - **Selecting opens the Product card side-card**, whose content comes from `_catalogDocFromApi` — the SAME builder the creation uses — fed as a `cloudSeed`. The card therefore shows colours, nozzle/bed/dryer temps, diameter, SKU, EAN and the catalogue link, and previews exactly what an add would store. The detail is fetched once per product, on click only, and cached for the session.
  - **A click selects, it never creates**: the only control that writes is a square `+` in the Product card's actions row, reusing the app's existing "+ material" affordance (`.flag-toggle--addmat`) — with the other actions rather than at the foot of the card, where it fell below the fold on any product with a full spec sheet.
  - **Every product type is browsable, only Filament is creatable.** `_catIsCreatable` refuses anything but Filament (142): `data1`–`data7` are per-type and only Filament is ratified, and a resin ships a `resin` block with no nozzle / dryer / bed. The user gets a plain-language "browse-only for now" message instead of silently-wrong data. To unlock, ratify the Resin slot contract in `playground/ttag-fields-editor` → `docs/TTAG-FIELDS.md`.
  - **Reuse, not duplication**: the `product/get` → doc mapping was extracted out of `_convertToPlus` into `_productApiFields`, and the full doc build into `_catalogDocFromApi`; the detail call reuses the existing `rfid:lookup-product` IPC.
  - **Telemetry**: new `cloudPlusAddedTotal` counter, separate from `cloudAddedTotal`. The stored `TigerCloud` analytics bucket key is untouched.
- **`.ttag` record contract, enforced at import.** A `.ttag` exists to **create TigerTag / TigerTag+ chips**, so a record must carry the full **chip payload**; everything else is enrichment metadata. Studio now refuses any material that doesn't (`TTAG_REQUIRED_NUM`, `_ttagRecordValid`, `_ttagMaterialValid`): 24 required fields (`uid` + the 10 identity ids + `measure` + the 4 colour bytes + `data1`–`data7` + `timestamp`), with `null`/`""` not counting as present. A **material is atomic** — a twin pair passes only if both sides do, so a half-twin is refused whole. Refused materials never reach the preview and are **counted and shown** (`ttagRejected`), never silently dropped; the write builder re-filters as a last line of defence — `renderer/inventory.js`.
- **`playground/ttag-fields-editor/`** — the **official dev tool** for the `.ttag` field contract, now documented in `CLAUDE.md` (new *".ttag field contract"* section) as the source-of-truth editor so every future session knows the contract is authored here, not hand-edited. Standalone dependency-free page: per-**product-type** tabs (142 Filament ratified · 116 Accessories · 41 Spare Part · 173 Resin · more to come), three independent axes per field (data **type** with real chip min/max ranges read from `parser.js`, **on-chip** toggle, **Required/Optional/N-A** per type), per-type "Why" notes (incl. the per-type meaning of `data1`–`data7`), live counters, filter, localStorage autosave. Regenerates `docs/TTAG-FIELDS.md` verbatim on **Download**. Workflow: founder evolves the contract here (anomalies, new types) → hands back the regenerated doc → an AI re-aligns the importer + propagates to TigerSystem-Docs / mobile.
- **`docs/TTAG-FIELDS.md`** — the ratified contract: **28 required · 44 optional**, of which **24/24 chip-payload fields required**. Documents the envelope, the chip payload, the enrichment metadata, the minimal well-formed record and the enforcement rules. Companion to the TigerSystem-Docs `ttag-format` spec.

## Changed
- **Long dropdown lists now show a scrollbar again.** The Brand / Material lists run to 25+ entries but the app hides scrollbars everywhere, so nothing said they scrolled. A fade alone does not fix it — it only reads as "there is more" when an item is visibly cut in half, and says nothing when the cut lands between two rows. `.csel-pop-list` is therefore the one list in the app that KEEPS its scrollbar (slim, on-theme, darkening on hover): it is unconditional, and it also answers "where am I" and "how much is left", which a fade cannot. The fade stays on both edges as a softener — `renderer/css/70-detail-misc.css`, `renderer/inventory.js`.
- **Scroll fade ("scroll shadow") is now a reusable utility, and the inventory views use it.** The `.ttag` import list had a one-off bottom fade; it is generalised as `.scroll-fade` (`00-base.css`) + `_wireScrollFade(el, { top })` (`renderer/inventory.js`), applied to both edges of the **option lists of every dropdown** (`.csel-pop-list`) and to **every scrolling list view**, both edges each: Inventory table (`#invTableWrap`) and grid (`#invGrid`), Favorites (`#invProductsView`, grid and table), Printers (`#invPrinterView` for the grid/cam wall plus the table's own `.pt-wrap` scroller) and Search (`#invCatalogView`, grid and table). Deliberately **off in the To-order view**: it is a card plus a sticky side panel, so masking the scroller would fade a panel that hides nothing — the cue belongs only where content is actually cut off. Where a sticky `<thead>` owns the top of the scrollport the top fade starts BELOW it — `--sf-top-offset` is measured from the header (not hard-coded, so it follows font and locale) and re-measured on every call, since switching a view between grid and table makes the header appear or vanish; keeps the header crisp while the rows slide under it. Note the app makes the header CELLS sticky (`thead th`), not the `<thead>`, so the check reads a `th` — and it also walks up to the scroller to make sure no intermediate wrapper traps the sticky, in which case there is no pinned header to offset under. Implemented as a `mask-image` on the scroller itself rather than a coloured overlay on a wrapper: a mask is relative to the element's own box so it never scrolls away with the content, needs no extra DOM, and fades to transparent so it works on any background. Both scrollers hide their scrollbar, which is precisely why the cue was missing. The helper returns its updater — call it after re-rendering, since neither `scroll` nor a resize of the element fires when only the content height changed.
- **The grid-view picto is a real icon.** Every "grid" view button used the `⊞` text glyph (the one control in the view selector without a proper icon) — it now uses `assets/svg/icons/icon_grid.svg` via the standard `.icon-grid` mask, at `icon-13` like its list sibling. Applied to all five: Inventory, Favorites, Printers, Search, and the Lists view's own layout toggle (whose "rows" button was already a real icon, leaving the glyph visibly odd next to it). The now-unused `.vt-glyph` rules are gone — `renderer/inventory.html`, `renderer/inventory.js`, `renderer/css/70-detail-misc.css`.
- **`_syncTtagBarButtons` → `_syncInvBarButtons`** — it now governs all three inventory action-bar buttons (.ttag Export/Import + "+ From Catalogue"), which share one visibility rule (material inventory, own account), so the name no longer claims to be .ttag-only — `renderer/inventory.js`.
- **Every user-facing web link moved off `tigertag.io` to the new `tigersystem.io` domains** (API endpoints `cdn`/`api.tigertag.io` are unchanged). Catalogue: the two "browse the TigerTag+ material list" buttons (help modal `productIdHelpListBtn` + upgrade-to-Plus `upgradePlusListBtn`) open `https://tigersystem.io/fr/catalog`, and the clickable **Product ID** (spool detail + product-info cards) opens `https://tigersystem.io/fr/catalog/<id>` (was `tigertag.io/pages/product-infos/<id>`). Shop: the "buy TigerTag RFID Maker" CTAs open `https://shop.tigersystem.io/collections/tigertag-rfid-maker` (was `tigertag.io/collections/...`) — `renderer/inventory.js`.
- **The mini dashboard counts TigerData+ on its own tile.** The header stat bar showed three tiers; it now shows four, and the plain TigerData count excludes the `+` ones (`isCloudPlus` is a subset of `isCloud`) so the four tiles still sum to the inventory. The tile reads how much of your digital-only stock the app can actually identify — `renderer/inventory.js`, i18n `statCloudPlusMini`.
- **Stat cards keep one shape whatever the bar's width.** `flex: 1 1 0` let a card be squeezed under its own content, so a long label ("Valeur du stock ⓘ") wrapped onto a second line and that card grew taller than its neighbours — visible with three tiles, unmissable with four. A `min-width: fit-content` floor plus `nowrap` on the value and the label keeps every card the same height; past that floor the bar scrolls horizontally, which it was already set up to do — `renderer/css/00-base.css`.
- **The container picker is finally in alphabetical order, and says when it scrolls.** Its 37 brand groups came out in the order containers had been ADDED to the catalogue, so finding one meant reading the whole list; they are now sorted by brand (case never decides the order, and `3DXTECH` sorts as a number), with the two generic "Customizable" containers pinned at the top — they are the fallback when your spool's brand isn't listed, and would be lost mid-list between Geeetech and GIANTARM. Keyed on `brandId == 0`, the same sentinel `resolveContainerForBrand` uses. The list also gets the standard `.scroll-fade` on both edges, re-applied after each search re-render: `.cp-list` hides its scrollbar, so nothing said the list continued past the fold — `renderer/inventory.js`.
- **Three container brand names pointed at the wrong record**: `Formfutura` carried Sunlu's brand id (`51857` → `53043`), and `GIANTARN` / `Prusa` were spellings the reference data doesn't use (`GIANTARM` / `Prusament`); `eSun` appeared under two casings. Every brand in the file now resolves to its own id — `data/container_spool/spools_filament.json`.
- **Two more spool containers to weigh against: Inslogic Masterspool Black (232 g) and Jayo Plastic Black (127 g)** — 49 → 51 entries. The bundled TigerTag reference data was regenerated at the same time (`db_update.py`), which is where both brand ids come from (Inslogic 2049, Jayo 7812) — `data/container_spool/spools_filament.json`, `assets/db/tigertag/id_brand.json`, `assets/img/spool_filament/` (2 illustrations, downsized to the folder's 256 px norm; masters archived in `assets-src/`).
- **`.ttag` export now uses the canonical vendor MIME `application/vnd.tigertag.ttag+json`** (was `application/json`) — aligns Studio with the TigerSystem-Docs `ttag-format` spec. Import is unaffected (it validates by content, never by MIME/extension) — `renderer/inventory.js` (`_saveTtagFile`).

## Fixed
- **The shop button was missing on a friend's spool.** Its whole point — "where do I buy this?" — matters most on someone else's shelf, but the button was gated owner-only along with "+ Material". It now shows in a friend view too, reading THEIR shared product rather than mine, and only when they actually have a link: with none, the empty-state route is the Reorder card, which is owner-only, so the button is dropped rather than left leading nowhere. "+ Material" stays owner-only — `renderer/inventory.js`.
- **The Search segment showed up while browsing a friend's shelf.** It exists to add a spool to YOUR inventory, so on a friend's account it was an offer the view can't honour (the "+ From Catalogue" button was already gated, the view switch was not). The group and its separator now hide like Printers does, and entering a friend while Search is open bounces you to the inventory grid rather than stranding you in a view whose buttons just disappeared — `renderer/inventory.js`.
- **The tier badges had lost their hairline border.** The shared capsule rule uses the `border` SHORTHAND, which resets the colour to transparent, and it sits after the per-tier rules — so `.tag-cloud`'s stronger edge (the one that lets a white capsule sit on a white card) has been invisible since v2.13.0, and TigerData+'s amber accent, the only thing saying "chipless, yet identified", was never visible at all. Both colours are now declared after the shared rule — `renderer/css/70-detail-misc.css`.
- **Adding a spool now shows you the spool.** The Product card's `+` opens the **grouped-spools deck** for that filament once the write comes back, so the new spool is visible next to the ones already owned instead of vanishing into the inventory. Keyed by product IDENTITY rather than doc id (the "+ Material" path only returns a count), with `keepSingletons` so the deck opens even for the first spool of that filament — `renderer/inventory.js`.
- **The grouped-spools deck says when each spool was added.** Every member of a deck is the same filament, so the arrival date is the only thing telling them apart — the deck now carries an "Added <ago>" line (`just now`, `3 days ago`, `2 months ago`) with the exact date on hover, read from the doc's own `timestamp`. `chipTsToMs` converts the chip epoch (seconds since 2000) and carries fmtChipTs's guard against old docs that stored a plain Unix stamp there, which would otherwise read three decades into the future — `renderer/inventory.js`, `renderer/css/70-detail-misc.css`.
- **A shopping button on the Product card and the spool detail.** One button with two jobs, told apart by colour — Shopify green (the Reorder card's own shop green) when the product has a buy link, and clicking opens the shop; plain when it has none, and clicking drops you on the Reorder card's buy-link field. So it always leads somewhere. Uses `icon-cart`, never the `icon-cart-plus` of the to-order flag beside it, so the two can't be confused — `renderer/inventory.js`, `renderer/css/70-detail-misc.css`.
- **The spool detail card now offers the same actions as the Product card.** Its actions row had only ⓘ / list / ❤ / ★, so adding another spool of the filament you were looking at meant hopping to another card. It now carries the same `+` (add a spool of this material, then open the grouped-spools deck on it) and the same shopping button, in the same order — the three cards showing one product finally propose one set of actions. Both are delegated handlers and the row joins the surgical refresh, so the shopping button turns green the moment a buy link is saved from the Reorder card, without rebuilding the panel — `renderer/inventory.js`.
- **The Product card looked different depending on where it was opened from.** It is one card and one renderer, but the content is built from `p.cloudSeed`: the Search views always hand it a full one (from `product/get`) while a favorite only carries what was captured the day it was starred, and the `+` action was gated to catalogue previews. Now every product card renders the same layout — the `+`, the result line and the footer note are unconditional, only the click ROUTE differs (a catalogue preview mints a TigerData+ via `_catalogCreate`, an owned product uses the existing `_createCloudFromProduct`) — and a card whose product carries a real `id_product` tops its seed up from the catalogue on open, so both routes show the same specs. The stored product is never mutated: the enriched seed goes into a copy — `renderer/inventory.js`.
- **The Favorites list lost its header on scroll.** `.pv-table-wrap` was a bordered box with `overflow: hidden` sitting inside the scrolling view, so the sticky `<thead>` pinned to that never-scrolling box and slid away with the content. It now follows the inventory `.table-wrap` recipe exactly — the bordered, rounded box IS the scroller (`flex: 1; min-height: 0; overflow: auto`) — which pins the header inside it, keeps the corners rounded while scrolling, and lets the scroll-fade sit on the element that actually overflows (flush under the header, only as wide as the table) — `renderer/css/70-detail-misc.css`.
- **The Search list squared off its rounded corners on scroll**, same cause as the Favorites one: `.cv-table-wrap` was `overflow: visible`, so the sticky header pinned to the outer view and escaped the rounded box. It now keeps `.table-wrap`'s own `overflow: auto` and is the scroller — corners stay rounded and the fade sits on it — `renderer/css/70-detail-misc.css`.
- **The printer list had no scroll fade at all.** `renderPrintersView` returns early for the table mode, so the wiring at its end never ran; it now lives inside `_renderPrinterTable`, where `.pt-wrap` actually exists. Its sticky header is the `<thead>` itself (`.pt-head`) while the inventory tables make the CELLS sticky, so the offset detection accepts either — reading only the cell left the offset at 0 and dimmed the header instead of starting below it — `renderer/inventory.js`.
- **Printer-list checkboxes painted over the sticky header.** `.pt-head` was `z-index: 1` while the row `.sel-check` is `z-index: 4`, so a row scrolling under the header showed its checkbox on top of it. Raised to 20, the value the inventory table's own thead uses — `renderer/css/40-printers.css`.
- **The Product card hid the catalogue link for anything chipless.** The "Product ID" row (which links to `tigersystem.io/…/catalog/<id>`) was gated on `isPlus`, so a TigerData+ — or a catalogue product previewed from the Search views — never showed it despite carrying a real `id_product`. Gated on the id being real (neither `0` nor `0xFFFFFFFF`) and nothing else — `renderer/inventory.js`.
- **Catalogue thumbnails showed nothing while loading, and stayed blank on a dead link.** `thumbHTML` renders the photo OR the colour square, never both. The Search table now stacks them like the inventory grid card does — the filament colour paints immediately and remains if the image errors out — and the Product card's illustration carries the colour behind it during load — `renderer/inventory.js`, `renderer/css/70-detail-misc.css`.
- **The Search views could not be scrolled with the wheel.** The page itself never scrolls (`html, body { overflow: hidden }`), so each view has to be its own scroller — `.inv-catalog-view` was missing the `flex: 1; min-height: 0; overflow-y: auto` recipe the other full-height views use, and its list was simply clipped — `renderer/css/70-detail-misc.css`.
