# Worklog — v2.25.0 (in progress)

## Added
- **Add a Bambu Lab printer with your account.** A third way in, beside scanning the network and typing an IP, and the easy one: an email address, the code Bambu sends back, and every machine on the account appears — each already carrying its own LAN access code, which the cloud simply hands over, so nothing has to be read off the printer's screen. Machines added this way are reached through Bambu's cloud, so they report from anywhere rather than only from the same network. The cloud broker sends the very same `print.push_status` the LAN one does, so cloud telemetry is emitted on the SAME channel and the parser, the cards, the job block, the temperatures, the AMS and every control are reused untouched — what differs is one client for the ACCOUNT instead of one per printer, and a token instead of a per-machine code. REST goes through Electron's `net` rather than node or fetch, deliberately: `api.bambulab.com` sits behind Cloudflare, which reads the TLS fingerprint, and Electron's `net` IS Chromium's stack. Expired and wrong codes are told apart, because one needs a new code and the other needs a better one. The account session — token, uid, region — is stored ONCE in `printers/bambulab/secrets/`, never on a machine's own record: Firestore hands out documents whole, so a secret sitting in a printer's record would travel with it the day printers become friend-visible — `main.js`, `preload.js`, `renderer/printers/bambulab/index.js`, `renderer/printers/bambulab/add-flow.js`, `renderer/printers/context.js`, `renderer/inventory.js`, `renderer/css/40-printers.css`
  - Machines are TICKED, one or several, and added together by a single key that carries the count. Adding one per click closed the panel each time, so taking three meant signing in three times over; a run where some fail says so and stays open rather than closing over a half-done job. Chosen cards are ringed in the accent at the boards' own offset.
  - The machines are offered with their PICTURE, laid out like a network-scan result, so an X1C is told from a P1P at a glance rather than by reading serial numbers; a raw dump of the account's machine list sits under them in debug mode only, with a copy key, for building on top of.
  - Sign-in verified end to end against a real account: the emailed code, the token, the uid and the machine list all come back — Cloudflare does not turn Electron's network stack away.
  - A cloud printer is CONNECTED like any other. Five gates in the renderer required an IP address before opening a Bambu connection, and a cloud machine has none — it is reached through the account's broker — so the printer was added, displayed, and then left permanently disconnected with an empty live block. They now accept a cloud printer, in the shape Anycubic already used.
  - **A cloud printer picks up its own LAN credentials, and its camera comes on by itself.** The cloud hands over the access code and the serial when the machine is added; the machine's own telemetry carries its address — advertised in the camera URL, or as a LITTLE-ENDIAN integer in its network block, where the first byte of the address is the low byte of the number. The three together are exactly what a printer added by hand on the network has, so the address is adopted once per connection, stored, and the camera started — nothing asked of the user. Verified against the address the spec records: `2585045184` → `192.168.20.154`.
  - A cloud printer arrives with its real model. The catalogue entry is resolved from the code the cloud reports, falling back to the serial's prefix; left unset it showed a "?" thumbnail and would have picked the wrong camera transport. `BL-P001` — what the cloud calls an X1 Carbon — was missing from the code table. A printer whose model never resolved now corrects itself from its serial on the first report, through the mechanism the add-by-IP flow already used for the same problem, so records written before this are repaired rather than left showing a "?".

## Changed
- The **+ beside the inventory search is a filled accent button** with a white glyph, instead of a grey `+` floating on nothing. It is the way in to adding a spool, and it sits inside a field that reads as somewhere to type — so it has to look like a button rather than an ornament — `renderer/css/70-detail-misc.css`
- **Add-a-product refuses a zero where a zero is not a measurement.** Weight, the two nozzle temperatures, the two bed temperatures and the drying pair now floor at 1, corrected AS YOU TYPE rather than refused at save: a lone `0` becomes `1` on the spot. The floor is read from each field's own `min`, the mirror of the ceiling that was already applied from `max`, so a field's bounds stay declared in one place. Typing is not fought — reaching 50 by typing `5` then `0` still works, since `50` is already above the floor. Empty stays empty: the drying pair is optional, and blank is how "needs no drying" is said. The save path enforces the same floor, for values that never passed through the keyboard — a material picked from the catalogue seeds these fields, and 7 of the 113 recommend a 0 — `renderer/inventory.js`, `renderer/inventory.html`
- **A printer reached through the cloud says so: its status dot IS a cloud.** Same colour code — green when it answers, grey when it does not — a different shape, on the board card and in the side panel, for BOTH brands that have a cloud mode (Bambu Lab and Anycubic), keyed off the `mode: "cloud"` they both already store. One mark carrying two facts beats two marks side by side. The glyph is drawn by a pseudo-element rather than by the dot itself, because masking is applied AFTER filtering: a glow put on a masked element — `box-shadow` or `drop-shadow` alike — is clipped away with everything outside the silhouette and never appears. Left unmasked, the dot carries the halo it already had, so a cloud breathes on exactly the same heartbeat as a round dot with nothing kept in step by hand. The icon is a new FILLED cloud (`icon_cloud_filled.svg`): masking the outline one painted only the outline, giving a hollow ring. Nothing distinguished them before, in either brand: the two do not behave the same once you leave the house — a LAN machine simply becomes unreachable while a cloud one keeps answering — so when one goes quiet, knowing which you are looking at is what tells you whether anything is actually wrong. Anycubic carried a `connLan` field whose comment claimed the card already did this; nothing read it — `renderer/inventory.js`, `renderer/css/40-printers.css`
- **The camera wall is a plan, like the two other boards.** Cameras are placed by hand on a surface you pan and zoom instead of flowing in a grid, and they are RESIZED FREELY by a grip in the corner — the ½× / 1× / 2× presets are gone, three answers to a question the user can now answer exactly. A camera's width travels with its position (`camWallPlan: {x, y, z, w}`, a field of its own since the printer board's camera widget already owns `camPlan` and the two are placed independently); only the width is stored, because the picture is 16:9 and the head is fixed, so one number describes the card. It has an **Arrange mode** like the other two, with the storage plan's own 24 px mesh scaled by the zoom: a card's HEAD is a handle in both modes — it is the part that is not the picture, so taking hold of it can never be mistaken for a click on the video, and no separate grip button is needed; arranging then extends the handle to the whole card, keeps the head visible and gives the LEFT BUTTON to the rubber band — sweeping and panning both start on empty surface, so one has to yield, and arranging is precisely when you mean to pick cards rather than travel; the wheel button pans in both modes, so the view is never trapped. Outside it the wall is a wall — pictures, heads on hover, and a small handle for the occasional move. Its plan bar is the other plans' bar to the character — same classes, same order, same numeric field with its own `%` beside it. Written differently it LOOKED different: a text field carrying the percent inside it takes the default width, which is why this one sprawled while theirs stayed a neat pill. Three views that behave alike have to be built alike. Its zoom is the other plans' zoom, down to the arithmetic: the same bounds, the same round-ten ladder, and the point under the cursor held still — a zoom that lets the surface slide under the pointer reads as something having MOVED, which on a view whose whole purpose is where things are is the wrong impression entirely. The wheel zooms with no modifier, as it does everywhere else, and ignores the stray notches a held-down wheel produces while panning. Moving a camera no longer opens its machine's side panel: the click that ends a drag lands on the card, and a panel sliding open over the wall you are laying out is the opposite of what you came for. Arranging suppresses it outright — the whole card is a handle there — and outside it the guard goes up the instant the gesture becomes a move, not when it ends: raised at the end it was raised after the writes were awaited, and the click following a release fires long before a round-trip to the database resolves, so it was always too late. The mesh appears the moment anything is taken or resized, in or out of Arrange: outside it nothing else says a gesture has become an edit — the card simply starts following the pointer — and a grid arriving under your hand explains the snapping before it happens. Dragging uses the storage plan's own magnetism and its guides: a card snaps flush to a neighbour's edge, or lines its edges and centres up with one, and a thin line says WHY it clicked into place — without it the magnetism reads as the card resisting. In a group the card actually grabbed is the one the magnetism speaks for and the rest follow at their own offsets, so the set keeps its spacing exactly. A card taken in the hand comes to the FRONT, and dropped last means dropped on top for good — the depth is written inline by the layout, which no stylesheet rule can outrank, so the lift is done on the element itself and restored from the record on release. A swept selection is ringed in the accent, 2 px at the same offset as the storage and printer boards — a selection has to look identical wherever it is made. Its states are written as one ordered block carrying the view's id, because the plain border arranging draws also carries it: at lower weight the selection was silently overruled, and hovering a selected card overruled it again. It reuses the shared primitives — the rubber band, the panning, the free-spot search — so the three views cannot drift apart in feel. A camera sent fullscreen now fills the SCREEN. `position: fixed` only ever covered the app window, so the title bar, the menu bar and the dock stayed in front of a view whose entire point is to fill the screen; the card is handed to the Fullscreen API instead, which puts it in the top layer at screen size and MOVES NO ELEMENT, so the stream inside it is not interrupted. The window-filling card remains as the fallback when the platform refuses. Leaving is believed rather than assumed: Escape, the green button and the system all end fullscreen behind the app's back, so the card's state is written from what the browser actually did — otherwise the key would go on claiming fullscreen over a card that had come back down. Widths are applied in their own pass before any position is computed: the free-spot search measures a card to find room for it, and a card not yet given its width measures whatever the stylesheet last left it, which dealt every camera a slot the wrong size and piled them on top of each other. ONE RULE GOVERNS IT: a card holds a live stream, so it is never recreated, only moved — every path positions existing elements, the drag writes the element and only the release touches the record, and the wall's existing patch mode is what keeps a size or state change from rebuilding anything. The drag-to-reorder went with the grid it served; `camSortIndex` now only orders cameras that have never been placed, on their first render. **A placed camera keeps its place when its machine goes quiet** — drawn at the same spot and the same size, dimmed and empty, and still movable and resizable while the printer is off. A wall that dropped a card the moment a machine slept destroyed the arrangement it exists to hold, and the hole it left was indistinguishable from a camera never placed. Only a camera that has never been placed is absent: there is nothing of it to preserve. Fullscreen still leaves the plan entirely: the layout stops writing inline geometry on a card while it is up there and clears what it wrote, because position, size and depth are written inline and no stylesheet can outrank that — a card sent fullscreen simply grew inside the surface instead of covering the window. The detached window is untouched — `renderer/inventory.js`, `renderer/css/40-printers.css`

## Fixed
- **The cloud preview blinked out and back on every redraw.** The FTPS route always handed the renderer image BYTES, so the preview field held something instant and self-contained; the cloud route handed it a URL on Bambu's CDN instead, and every DOM rebuild re-requested it, leaving the picture blank for as long as the round-trip took — the media-reload trap the surgical-update rules warn about, arriving through the data rather than through the markup. The image is now fetched once in the main process and returned as a data-URI, cached by source URL, so both routes deliver the same kind of value and a card can be redrawn as often as it likes. The comparison that decides whether to fetch is made on the source URL, not on what is stored, or the decoded image would never match and every pass would fetch again. If the decode fails for any reason the raw URL is used instead: the worst case is then the flicker this set out to remove, never a blank card — `main.js`, `preload.js`, `renderer/printers/bambulab/index.js`
- **A cloud Bambu printer keeps showing what it last made.** The preview and the job's name survive the print now, on the board card and in the side panel, instead of the card falling back to a stock photo of the printer the moment the machine goes quiet — the space stays filled and the last thing a printer made is more use than a picture of the printer. Both come from the cloud for a cloud machine: `cover` and `title` off the account's task list, which still holds them once telemetry has stopped naming anything. A LAN printer still loses its preview when it goes idle: the `.3mf` it was read from does not outlive the job, so keeping the image would eventually be a lie. The board card was gating on the print state too and had to learn the same thing — the driver decides, the view trusts the field — `renderer/inventory.js`, `renderer/printers/bambulab/{index,cards}.js`
- **A cloud Bambu printer never showed the print's preview away from home.** There was exactly one way to fetch it — FTPS straight to the machine — which works only on the printer's own network, so a printer added by signing in, whose whole point is reporting from anywhere, had no preview anywhere else. A cloud printer now takes the account's task list (`/v1/user-service/my/tasks`), where each entry carries `cover`: a plain HTTPS image on Bambu's CDN, no auth of its own. Cloud printers take that route and only that one — FTPS to a machine on another network does not fail fast, it hangs until it times out, once per retry window, for nothing. The list is the ACCOUNT's twenty most recent tasks rather than this machine's current one, so it is filtered by device and then narrowed by the job's own name, falling back to the most recently started; taking the first match would eventually show a previous print. Endpoint and payload shape were taken from the maintained Home Assistant integration rather than guessed — the first endpoint written here, lifted from our own spec notes, was the wrong one — `main.js`, `preload.js`, `renderer/printers/bambulab/index.js`
- **Resizing a camera opened — or closed — its machine's side panel.** The drag already guarded against this; the resize grip never did, so the click the release produces landed on the card and was taken for a request to open the printer. The guard now goes up on the first MOVEMENT of a resize, as it does for a drag and for the same reason: raised on release it would be raised after the write is awaited, and the click fires long before that round-trip resolves. It is lowered on a timer scheduled BEFORE that await too — lowered after it, a slow write would leave the guard up and swallow the next honest click — `renderer/inventory.js`
- **A Bambu print showed no preview, and carried the wrong name.** The hint used to find the model was `gcode_file` — a path INSIDE the archive, `/data/Metadata/plate_1.gcode` — while the `.3mf` sitting on the printer is named after the job: `TigerPod_Mini_A1.3mf`. The lookup therefore searched for `plate_1.3mf`, which exists nowhere, and no preview was ever found; the same value put `plate_1.gcode` on the card where Bambu's own app shows the project's name. The job name comes first now, the gcode path remaining the fallback for a print started without one. A cloud printer gets its preview too, on the same network — it holds an address and an access code like any other — `renderer/printers/bambulab/index.js`
- **A Bambu printer stopped reporting anything the moment a print FAILED** — filament, temperatures, job, all of it. `print.state` is a NUMBER on this firmware (7 on an X1C), and the state normaliser called `.toLowerCase()` on it. That runs on the FIRST line of the merge, so the exception took the whole message down: nothing after it was ever read. The board fell back to the external spool alone. It only fires when the printer reports FAILED or ERROR — the branch that looks for a second opinion on a failure — which is why it lay dormant for months and surfaced the day a print failed. Only string candidates are considered now — `renderer/printers/bambulab/index.js`
- **A Bambu printer's AMS was recorded as ABSENT and stayed that way across restarts.** The units a driver reports are treated as the whole truth by the layer that stores them: anything it does not mention is written `present: false` onto the machine's record. But a printer sends one complete state and then DELTAS, and a delta carries no filament — so a connection questioned before its full state arrived answered with the external spool alone, and the AMS was filed as gone. Reloading did not help: the damage was in Firestore, not in memory. Units are now reported only once a full state has actually been seen (`msg: 0`, or any payload carrying an AMS block, since some firmwares omit the field), so a half-filled connection stays silent and the stored record is shown meanwhile, marked stale. The record repairs itself on the next complete state — `renderer/printers/bambulab/index.js`
- **A cloud printer's filament slots vanished moments after connecting.** Learning its own address (from its telemetry) made the renderer read it as a different machine on the very next tick: the record still held no address until Firestore echoed the write back, so the address check failed, the session was torn down and rebuilt with empty data — and rebuilt again, and again, in a loop that also wrote to Firestore on every status push. The AMS disappeared each time because after the first full state a printer sends only DELTAS, which carry no filament, and the full state they apply to had just been thrown away. A cloud connection is now exempt from that check outright: it runs on the account's broker, never on an address, so an address it has merely learned can never read as a different machine. The address is written only when it actually differs from the record — `renderer/inventory.js`, `renderer/printers/bambulab/index.js`
- The shared cloud client is re-pointed at the window that asks for it. It lives in the main process and outlives a renderer reload, so it went on posting telemetry to a page that no longer existed — `main.js`
- **`npm run i18n:add --json` was silently writing `"[object Object]"` into all nine locales.** Its JSON path coerced every value with `String(v)`, which turns a `{one, other}` plural into that literal text — no error, no warning, nine files corrupted at once. It now emits plurals as real multi-line objects (matching how the locale files already write them), REFUSES anything that is neither a string nor a plural rather than coercing it, and replaces a plural already in the file as a whole block, so running the same command twice no longer leaves orphaned lines behind. — `scripts/i18n-add.mjs`
- **`bulkHiddenWarn` shipped broken in v2.16.0 and stayed broken for nine releases**, caught by the fix above: selecting rows and then filtering showed the literal text `[object Object]` where the warning belongs. It is the warning that says part of your selection is hidden — the one standing between you and a destructive action aimed at items you cannot see. Restored as a proper plural in 9 locales — `renderer/locales/*.json`
- **The camera view's fullscreen key is a switch again.** It was hard-wired to "fullscreen", so pressing it while already fullscreen asked for fullscreen a second time — which is nothing. Escape and a click on the picture were the only ways back, and a key that visibly does nothing reads as broken. It now carries the state it will PUT YOU IN, with the icon and the label to match, and it is flipped in place rather than re-rendered, because the card it sits on holds a live stream — `renderer/inventory.js`
- **The app no longer dies on an Intel Mac when a camera starts.** Three defects sat in a line, each one enough on its own. The Intel build shipped an Apple-Silicon ffmpeg: `ffmpeg-static` downloads ONE binary, for the machine doing the install, and GitHub's macOS runners are Apple Silicon — so both DMGs carried the arm64 binary. `scripts/prepare-ffmpeg.mjs` now fetches one binary per architecture before packaging and `build/afterPack.js` puts the right one into each app, before signing so it is signed with the bundle; both read the Mach-O header and REFUSE to continue on a mismatch, because shipping the wrong one silently is the whole failure. That staging also works around the installer skipping a download whenever a binary is already present, without ever looking at its architecture. Second, ffmpeg detection trusted `accessSync(X_OK)`, which answers "is this file executable" and never "can THIS cpu execute it" — the unusable bundled binary was adopted and Homebrew's perfectly good one, next in line, was never reached; each candidate is now asked to run before it is trusted, which also catches a missing library, a quarantined file or a truncated download. Third, both spawn sites were unguarded: `spawn` throws SYNCHRONOUSLY on a bad CPU type, on the assignment itself, so the `proc.on('error')` handler registered on the next line never existed yet — the failure reached the main process as an uncaught exception and Electron put a crash dialog in front of the user, for a camera that simply could not start. Both are wrapped now, and a camera that will not start is a camera that will not start. — `main.js`, `scripts/prepare-ffmpeg.mjs`, `build/afterPack.js`, `build/sign-and-notarize.sh`, `package.json`
- The bare `ffmpeg` fallback on PATH was never reachable: it was tested with `accessSync`, which resolves a bare name against the working directory instead of PATH — `main.js`
